Loop Engineering บน Claude Code

Coordinator → Worker → Reviewer → เปิด MR → คุณตรวจขั้นสุดท้าย · รันด้วย launchd + claude -p บน Mac

1. Goal

เปลี่ยนจากการสั่ง AI ทีละคำสั่ง เป็นระบบที่วนทำงานเองทุกวันตอน 9:15 (ถ้าผลดีค่อยเพิ่มความถี่) ระบบจะหยิบเฉพาะ ticket ของคุณที่เสี่ยงต่ำ ทำทีละงาน จนได้ MR ที่มี evidence ครบรอคุณตรวจ คนที่สั่ง merge มีแค่คุณเท่านั้น (ระดับ L2)

2. Steps

Step 1 · Triage แบบ L1 (อ่านแล้วรายงานอย่างเดียว) ติดตั้งแล้ว 19/10

  • skill ~/.claude/skills/loop-triage/SKILL.md อ่าน Jira, GitLab และ Notion แล้วแนะนำ type:, risk: และ agent:ready หรือ needs:human
  • ตัวรัน ~/loop/bin/loop-run.sh ทำงานตามลำดับ: กันรันซ้อนด้วย lock → รอเน็ต → เรียก claude -p พร้อม allowlist ที่อ่านได้อย่างเดียว → เขียน log → เด้ง notification ถ้ามีของใหม่
  • launchd ~/Library/LaunchAgents/com.example.loop.plist สั่งรันทุกวันตอน 9:15 ถ้าตอนนั้นเครื่องหลับ จะรันชดตอนเครื่องตื่น (ถ้ายังอยู่ในช่วง 9–18)

✔ วิธีเช็ค: เปิด ~/loop/logs/YYYY-MM-DD.md แล้วเทียบกับ Jira ด้วยตัวเอง รายการและ label ที่แนะนำต้องตรงกับที่คุณคิด 3 วันทำงานติด

Step 2 · Worker แบบสั่งเอง ติดตั้งแล้ว 20/10

  • skill /loop-work <ticket> ทำงานตามลำดับ: สร้าง worktree ที่ ~/Projects/.loop-worktrees/<ticket> → อ่าน CLAUDE.md ของ repo → เขียนโค้ดและ test → รัน test กับ pipeline job บนเครื่อง → ใช้ /ship ถ้า repo มี (web-app) ถ้าไม่มีใช้ glab mr create → ติด label owner:you + needs:human-verify แล้วเช็คว่าติดจริง → comment ลิงก์ MR ไว้ใน ticket
  • e2e ด้วย Claude in Chrome จะรันเฉพาะเมื่อคุณสั่ง ถ้าเป็นงานที่ไม่ใช่ UI ให้เขียนขั้นตอน verify แบบ manual ไว้ใน MR
  • skill /merge-approved <ticket> (คุณสั่งเองที่หน้าเครื่อง) จะถอด label ออกแล้ว merge แบบ squash + ลบ source branch

✔ วิธีเช็ค: สั่งเองแล้วได้ MR ดี 2 ตัวขึ้นไป label ครบ test ผ่าน และงานที่คุณเปิดค้างไว้ไม่ถูกกระทบ

Step 3 · Reviewer sub-agent ติดตั้งแล้ว 20/10

  • ก่อนเปิด MR ให้ /loop-work เรียก Reviewer ตัวที่แยกจาก Worker มารัน simplify + code-review ตาม pattern ของ repo จากนั้น Worker แก้ findings แล้วแนบผล review ไว้ใน MR
  • Reviewer ให้ได้แค่ evidence ไม่มีสิทธิ์ approve

✔ วิธีเช็ค: MR 2 ตัวมีส่วน "Review findings" และคุณเห็นว่าจับปัญหาได้จริง

Step 4 · ตั้งเวลาให้ Worker ติดตั้งแล้ว 20/10

  • เพิ่มใน loop-run.sh: หลัง triage เสร็จ ถ้ามี ticket ที่คุณติด agent:ready ไว้ และไม่มีงานค้าง ก็เรียก /loop-work 1 งาน
  • เช็ค RAM ก่อนเริ่ม ถ้าเหลือน้อยให้ข้ามรอบแล้วจดลง log จบรอบแล้วต้องไม่มีโปรเซส karma หรือ headless Chrome ค้าง
  • allowlist ของ Worker ให้แก้ไฟล์ได้เฉพาะใน worktree ใช้ git/glab ได้ตามที่จำเป็น ส่วน force push, merge และการอ่าน .env* ห้ามเสมอ

✔ วิธีเช็ค: รันอัตโนมัติ 1 สัปดาห์ ได้ MR ที่ใช้ได้โดยไม่มีงานรันซ้อนกัน

Step 5 · ให้ Coordinator ติด label เอง ติดตั้งแล้ว 20/10 · ติด label แล้ว 11 ใบ

  • triage เปลี่ยนจากรายงานเฉยๆ เป็นติด label จริง agent:ready ติดได้เฉพาะงานที่เข้าเกณฑ์ risk:low ครบทุกข้อ ถ้าไม่ชัดให้ติด needs:human พร้อมคำถาม

✔ วิธีเช็ค: 1 สัปดาห์ไม่มี agent:ready ที่คุณต้องถอดออกเอง

3. Success criteria

  • ทุกรอบจบที่ MR รอตรวจ: ไป staging หรือ develop, ผูกกับ ticket, มี label needs:human-verify + owner:you
  • MR มี evidence ครบ: ผลของ simplify และ review จาก Reviewer, คำสั่ง test และ pipeline ที่รันพร้อมผล, รูปจาก e2e หรือขั้นตอน verify แบบ manual
  • ไม่เคยแตะ ticket ของคนอื่น ไม่เคยทำ 2 งานพร้อมกัน และไม่เคย merge เอง
  • เรื่องที่ไม่ชัดถูกส่งไป needs:human ทั้งหมด ไม่มีการเดาเอง

4. Out of scope

  • L3 (AI merge เอง) และการ deploy
  • รันบน Cloud หรือ GitLab CI ตอนปิดเครื่อง และการตั้งเวลาปลุกเครื่องด้วย pmset
  • repo อื่นนอกจาก web-app กับ project-b-web จนกว่า repo นั้นจะมี CLAUDE.md
  • การแก้ ship.sh และ Paperclip (ปิดไว้แล้ว ข้อมูลยังอยู่ที่ ~/.paperclip)

5. Risks / open questions

  • ผล triage ไม่เหมือนกันทุกรอบ: สองรอบติดกันได้ needs:human 4 กับ 5 ใบ ใน Step 5 ต้องกำหนดเกณฑ์ให้ตายตัวกว่านี้
  • macOS TCC: launchd เข้า ~/Documents ไม่ได้ ระบบจึงอยู่ที่ ~/loop ส่วน Worker ที่ต้องอ่าน standup ใน Documents จะติดเรื่องเดียวกัน
  • Stop hook: session-digest.sh รันหลังทุก session รวมถึงรอบของ loop ด้วย อาจทำให้ standup digest มีข้อมูลของ loop ปนเข้ามา
  • GitLab account ร่วม: คำสั่งที่พิมพ์ใน MR comment ไม่น่าเชื่อถือ การ merge จึงต้องสั่งที่หน้าเครื่องเท่านั้น
  • ช่วงเครื่องหลับ: รอบที่พลาดไปจะถูกรันชด 1 ครั้งตอนเครื่องตื่น และมีขั้นรอเน็ตไม่เกิน 2 นาทีแล้ว
