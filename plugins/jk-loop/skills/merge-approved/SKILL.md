# Merge approved (user-run)

The user invoking this is the explicit merge request for this one MR. Never merge any other MR. Read `~/loop/workspace.md` first. It runs in a normal session or in the task's Worker session: every step below uses a command the Worker is allowed.

1. Run `~/loop/bin/loop-merge <task>`, exactly that command with nothing joined to it. It is the only way this skill merges: never `git push`, `glab mr update` or `glab mr merge` by hand. It reads `repo`, `branch` and `mr` from loop-state (it needs `status=mr-open`) and checks the gates: the owner label from `LOOP_MR_LABELS` present, `needs:e2e` absent, head pipeline not failed, no unresolved threads, no conflict with the base, a `PASS` or `PASS+NOTES` verdict from `loop-verdict` on the patch that would land, target is the repo's base branch, and for the release repo the merge-back gate (`origin/staging..origin/master` must count `0`). Then it removes `needs:human-verify` (and the Draft flag of an MR opened before Loop MRs opened ready) and merges: on the shared gitlab.com account a local squash plus `--no-ff` merge commit in a temporary worktree, pushed with a lease on the branch head it read; on a self-hosted GitLab `glab mr merge --squash --remove-source-branch`. `~/loop/bin/loop-merge --dry-run <task>` checks the gates and changes nothing.
2. Act on its last line:
   - `refused: <reason>`: stop and report the reason; nothing was merged. `needs:e2e` means run `/jk-loop:e2e <task>` first, or, when the user says to skip e2e, `~/loop/bin/loop-mr <task> e2e-done` and run `loop-merge` again. A verdict that is `none`, `stale` or `FAIL` means no agent that did not write the code has passed the patch that would land: in the task's Worker session start a `loop-verifier` agent for the task and run `loop-merge` again on a `PASS`; in any other session say so and stop. When the user says they verified it by hand, write what they checked to a notes file, run `~/loop/bin/loop-verdict <task> PASS <notes file>`, then `loop-merge` again. Squash conflicts name the files: resolve them on the task's branch, push with `~/loop/bin/loop-push`, wait for the pipeline and run it again. A protected-branch refusal means the merge must be done on the web and will show the shared account's name. A pending merge-back means wait for it.
   - `merged <merge sha> <MR URL>`: go on, and report any `loop-merge:` line it printed before (a note it could not post, a branch it kept on origin).
3. Workspace: `transition_task <task>` to the space's "After merge" status from `workspace.md`, and `add_comment` `🤖 [loop-status] merged: <MR URL>`. Then read the card back with `get_task <task>` and `list_comments <task>`: report the card as a link with the status it shows now, and say so plainly when the status did not move or the comment is missing. Never report the merge as done before this check.
4. Run `~/loop/bin/loop-preview stop <task>` first: a running dev server writes into the worktree. Run `~/loop/bin/loop-state set <task> merged`, then `~/loop/bin/loop-clean`, which archives the task's spec and design package, removes its leftover MR text and removes its worktree when it is clean. In the task's Worker session the worktree is this session's folder, so `loop-clean` keeps it (`this session runs in it`) and the next run's `loop-clean` removes it. Report its `cleanup:` line, and say so plainly when it kept the worktree for uncommitted changes.
