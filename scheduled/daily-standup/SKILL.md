# Daily Standup Report

สร้างรายงาน Daily Standup จากงานจริงที่ทำ แล้วจัดรูปแบบสำหรับโพสต์ใน Discord
ผู้อ่านหลักคือ PO ซึ่งจะนำไปให้ AI สรุปต่อ ดังนั้นโครงสร้างต้องคงที่ทุกวัน และเนื้อหาต้องอ่านเข้าใจได้โดยไม่ต้องเปิดโค้ด

## Config (อ่านจาก environment ถ้ามี ไม่มีให้ใช้ค่า default)
- `STANDUP_NAME` — ชื่อที่แสดง (default: `git config --global user.name`)
- `STANDUP_REPO_ROOTS` — โฟลเดอร์ที่เก็บ repo คั่นด้วย space (default: `~/Projects`)
- `STANDUP_OUT_DIR` — ที่เก็บไฟล์รายงานและ session digest (default: `~/Documents/work/standups`)
- `DISCORD_WEBHOOK_URL` — ถ้ามี ให้โพสต์ลง Discord อัตโนมัติ

## Step 1 — กำหนดช่วงเวลา
ใช้ timezone Asia/Bangkok
- `NOW` = เวลาที่เริ่มรัน (`TZ=Asia/Bangkok date "+%Y-%m-%d %H:%M"`) จดไว้ใช้ใน Step 6
- `LAST` = เนื้อหาของไฟล์ `$STANDUP_OUT_DIR/.last-run` (รูปแบบ `YYYY-MM-DD HH:MM`)
- `SINCE` = ค่าที่เก่ากว่าระหว่าง `LAST` กับ "วันนี้ 00:00" ถ้าไม่มีไฟล์ ให้ใช้วันนี้ 00:00
  - รันซ้ำในวันเดียวกัน → รายงานยังครอบคลุมทั้งวัน (ไฟล์ของวันนี้ถูกเขียนทับด้วยฉบับล่าสุด)
  - รันครั้งแรกของวัน → รวมงานหลัง standup รอบก่อนด้วย (เช่น ช่วงค่ำเมื่อวาน หรือเสาร์–อาทิตย์)

## Step 2 — เก็บข้อมูลจาก session digest
ห้ามอ่านไฟล์ `.jsonl` ใน `~/.claude/projects` โดยตรง ให้ใช้ digest ที่ script เตรียมไว้
1. อัปเดต digest ให้ครบก่อน: `~/.claude/scheduled-tasks/daily-standup/session-digest.sh --sweep`
2. Digest อยู่ที่ `$STANDUP_OUT_DIR/sessions/YYYY-MM-DD/<project>__<session>.md` หนึ่งไฟล์ต่อหนึ่ง session ต่อหนึ่งวัน ให้อ่านทุกไฟล์ในโฟลเดอร์วันที่ตั้งแต่วันของ `SINCE` ถึงวันนี้ อ่านทั้งไฟล์ ไม่ต้องตัดต้นตัดท้าย
3. ในโฟลเดอร์วันของ `SINCE` ให้นับเฉพาะหัวข้อ `### HH:MM` ที่เวลาหลัง `SINCE`
4. หัวไฟล์บอก Project, path, Branch ถ้ามีบรรทัด `Continues earlier work. First prompt ...` แปลว่าเป็น session ที่ทำต่อจากวันก่อน ใช้บรรทัดนั้นเพื่อเข้าใจว่าเป็นงานอะไรเท่านั้น ห้ามนับเป็นงานของรอบนี้
5. จดว่าแต่ละ session: ทำอะไร / เสร็จหรือค้าง / เจอ error ที่ยังแก้ไม่ได้หรือรอคนอื่นไหม
6. ข้าม session ที่ไม่ใช่งาน เช่น แค่เปิด tool, ถามความรู้ทั่วไป, ปรับ config/memory ส่วนตัวของ Claude
7. ถ้าไฟล์ `$STANDUP_OUT_DIR/sessions/.errors.log` มีบรรทัดที่เวลาหลัง `SINCE` ให้แจ้งในหัวข้อ Notes ว่า digest ของบาง session อาจไม่ครบ

## Step 3 — เก็บข้อมูลจาก git ในเครื่อง
1. หา repo: `find $STANDUP_REPO_ROOTS -maxdepth 4 -name .git -prune 2>/dev/null` และเพิ่ม repo จาก path ในหัวไฟล์ digest ของ Step 2 ที่อยู่นอกโฟลเดอร์เหล่านี้
2. แต่ละ repo:
   - Commit ของเราในช่วงเวลา:
     `git log --all --since="$SINCE" --author="$(git config user.email)" --date=format:"%d/%m %H:%M" --pretty=format:"%h|%ad|%D|%s" --shortstat`
   - งานที่ยังไม่ commit: `git status --short` และ `git diff --stat` → ใช้เป็นข้อมูล In Progress
   - branch ปัจจุบัน และ push แล้วหรือยัง: `git branch --show-current`, `git rev-parse --abbrev-ref @{u}`
3. ข้าม repo ที่ไม่มีความเคลื่อนไหวในช่วงเวลา

## Step 4 — วิเคราะห์และจัดกลุ่ม
- **จัดกลุ่มเป็น "เรื่อง"** (topic) = 1 ticket หรือ 1 feature/งานใหญ่ เช่น `[EX-468] AI Agent — Knowledge base`, `LLMs-friendly Docs`
  - ดึงเลข ticket (regex `[A-Z][A-Z0-9]+-\d+`) จากชื่อ branch, commit message และชื่อ/เนื้อหา session ถ้ามีให้ใส่ในชื่อเรื่อง
  - งานที่ไม่มี ticket ให้ตั้งชื่อเรื่องตาม feature/branch เป็นภาษาที่ PO เข้าใจ
  - งานเล็กที่ไม่เข้าเรื่องไหน รวมไว้ในเรื่อง `🛠 อื่น ๆ`
  - ใช้ชื่อเรื่องเดียวกันทุกหัวข้อ (Done / In Progress / Next / Blockers) เพื่อให้ AI ของ PO จับคู่ได้
- รวม commit + session ที่เป็นงานเดียวกันเป็น bullet เดียว ไม่ต้องลิสต์ทุก commit (ดูกฎ 1 เรื่อง = 1 ประโยค ใน Step 5)
- **Done** = commit แล้วและ session จบด้วยผลสำเร็จ
- **In Progress** = มีโค้ดที่ยังไม่ commit, ยังไม่ push/MR, branch WIP หรือ session จบกลางทาง → ประเมิน % คร่าว ๆ เฉพาะเมื่อมีหลักฐานชัด
- **Next** = งานที่จะทำต่อพรุ่งนี้ อนุมานจาก In Progress และสิ่งที่ session บอกว่ายังเหลือ
- **Blockers** = เฉพาะที่มีหลักฐาน (error ที่ยังแก้ไม่ได้, รอ spec/API/review จากคนอื่น) ห้ามแต่งขึ้นเอง ถ้าไม่มีให้เขียน `ไม่มี 🎉`
- งานที่ทำต่อจากวันก่อนให้รายงานเฉพาะส่วนที่ทำในช่วงเวลานี้ และต่อท้ายว่า `(ต่อจากเมื่อวาน)`
- งานที่ไม่ได้ทำวันนี้ (อยู่ในช่วงเวลาเพราะทำหลัง standup รอบก่อน) ให้ต่อท้าย bullet ว่าทำเมื่อไร เช่น `(เมื่อวานช่วงค่ำ)` หรือ `(เสาร์)`

## Step 5 — เขียนรายงาน
กฎการเขียน:
- ภาษาไทย ศัพท์เทคนิคใช้ภาษาอังกฤษได้
- เขียนเป็น "ผลลัพธ์ที่ได้" ไม่ใช่ชื่อไฟล์ เช่น "หน้า Login เชื่อม API ได้แล้ว" แทน "แก้ LoginPage.tsx"
- **1 เรื่อง = 1 bullet = 1 ประโยคสั้น ต่อหัวข้อ** ห้ามแตกเรื่องเดียวกันเป็นหลาย bullet
- **ผลลัพธ์นำ แล้วตามด้วยสถานะหรือเหตุผล**: ขึ้นต้นด้วยสิ่งที่ได้ (มองจากมุมผู้ใช้/PO) ปิดท้ายด้วยสถานะ ("รอ deploy พุธ 4 พ.ย.") หรือเหตุผลถ้ายังใช้ไม่ได้ ("แต่ยังเปิดใช้ไม่ได้ เพราะ…")
- ยาวไม่เกิน ~100 ตัวอักษร (ประมาณ 15–25 คำ) ห้ามร้อยหลายขั้นตอนต่อกันด้วยคอมมา
- ตัดขั้นตอนระหว่างทางที่ PO ไม่ต้องใช้ตัดสินใจ (สร้าง draft ใน CMS, ตัด tag, ลง CR Sheet, ชื่อ task เช่น T9, test x/x) ใส่เลข MR/เวอร์ชันเฉพาะเมื่อ PO ต้องใช้อ้างอิง
- Blocker = ปัญหาที่กระทบผู้ใช้/งาน + สิ่งที่ต้องทำเพื่อปลด + `→ @คนที่ต้องทำ`
  - ❌ `- สร้าง draft 3 หัวข้อใน CMS, แก้ให้ลิงก์ #section เลื่อนถึงหัวข้อ (ผ่าน staging), ตัด tag v1.1.4, ลง CR Sheet และอัปเดตการ์ดว่าต้อง build+deploy ด้วย`
  - ✅ `- เอกสาร 3 หัวข้อใหม่พร้อมขึ้นจริงแล้ว รอ deploy วันพุธ 4 พ.ย.`
  - ✅ `- หน้าซื้อ Point และจ่ายบัตรทำเสร็จแล้ว แต่ยังเปิดใช้ไม่ได้ เพราะระบบส่งแพ็กเกจรายเดือนมาแทน Top-up`
  - ✅ Blocker: `- ลูกค้าเชื่อม Instagram บน prod ไม่ได้ ต้องแก้ค่า redirect บน server → @BE/DevOps`
- ใช้หัวข้อตาม template เป๊ะ ๆ ทุกวัน (PO ใช้ AI สรุปต่อ โครงสร้างต้องคงที่)
- ใต้แต่ละหัวข้อ ใส่ชื่อเรื่องเป็นบรรทัดตัวหนา `**emoji ชื่อเรื่อง**` แล้วตามด้วย bullet ของเรื่องนั้น ข้ามเรื่องที่ไม่มีอะไรในหัวข้อนั้น
- ห้ามใส่ secret, token, ค่าใน .env, ข้อมูลลูกค้า, IP/hostname ของ server, path ส่วนตัว หรือเรื่องสุขภาพ/ส่วนตัวของคนอื่น (ใช้คำว่า "ลางาน" แทน "ลาป่วย")

**ความยาวรวมต้องไม่เกิน 2000 ตัวอักษร** (นับทั้งข้อความ รวม header) ถ้าเกิน ให้ตัดตามลำดับนี้จนพอดี:
1. ย่อ Notes เหลือเรื่องที่ PO ต้องรู้ หรือลบหัวข้อ Notes
2. ย่อประโยคของแต่ละเรื่องให้สั้นลง (ยังคง 1 ประโยคต่อเรื่อง)
3. ตัดรายละเอียดตัวเลข/ชื่อเทคนิคที่ PO ไม่จำเป็นต้องรู้
ห้ามตัด Blockers และห้ามตัดเรื่องทั้งเรื่องออกจาก Done

## Step 6 — บันทึกและส่ง
1. นับความยาวจริงก่อนส่ง (เช่น `python3 -c "import sys;print(len(open(sys.argv[1]).read()))" <file>`) ถ้าเกิน 2000 ให้กลับไปตัดตาม Step 5
2. บันทึกไฟล์ที่ `$STANDUP_OUT_DIR/YYYY-MM-DD.md` (วันที่ของ `NOW`) เขียนทับได้ถ้ารันซ้ำวันเดียวกัน
3. ถ้ามี `DISCORD_WEBHOOK_URL` ให้โพสต์เป็นข้อความเดียว โดยใช้ `jq` สร้าง JSON เพื่อ escape ให้ถูกต้อง:
   `jq -n --arg c "$REPORT" '{content:$c}' | curl -sS -H "Content-Type: application/json" -d @- "$DISCORD_WEBHOOK_URL"`
4. ถ้าไม่มี webhook ให้แสดงรายงานใน code block เดียวพร้อม copy
5. เมื่อทำข้อ 1–4 เสร็จ (หรือไม่พบงานเลย) ให้บันทึกเวลารอบนี้: `printf '%s\n' "$NOW" > "$STANDUP_OUT_DIR/.last-run"` ถ้ารอบนี้ล้มเหลวกลางทาง ห้ามเขียนไฟล์นี้ เพื่อให้รอบถัดไปเก็บงานช่วงนี้ซ้ำ
6. จบด้วยสรุป 1 บรรทัด: บันทึกไฟล์ที่ไหน, ความยาวกี่ตัวอักษร และโพสต์ Discord สำเร็จหรือไม่
