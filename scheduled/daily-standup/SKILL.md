# Daily Standup Report

สร้างรายงาน Daily Standup จากงานจริงที่ทำ แล้วจัดรูปแบบสำหรับโพสต์ใน Discord
ผู้อ่านหลักคือ PO ซึ่งจะนำไปให้ AI สรุปต่อ ดังนั้นโครงสร้างต้องคงที่ทุกวัน และเนื้อหาต้องอ่านเข้าใจได้โดยไม่ต้องเปิดโค้ด

## Config (อ่านจาก environment ถ้ามี ไม่มีให้ใช้ค่า default)
- `STANDUP_NAME` — ชื่อที่แสดง (default: `git config --global user.name`)
- `STANDUP_REPO_ROOTS` — โฟลเดอร์ที่เก็บ repo คั่นด้วย space (default: `~/Projects`)
- `STANDUP_OUT_DIR` — ที่เก็บไฟล์รายงานและ session digest (default: `~/Documents/work/standups`)

## Step 1 — กำหนดช่วงเวลา
ใช้ timezone Asia/Bangkok
- `NOW` = เวลาที่เริ่มรัน (`TZ=Asia/Bangkok date "+%Y-%m-%d %H:%M"`) จดไว้ใช้ใน Step 6
- `LAST` = เนื้อหาของไฟล์ `$STANDUP_OUT_DIR/.last-run` (รูปแบบ `YYYY-MM-DD HH:MM`)
- `SINCE` = ค่าที่เก่ากว่าระหว่าง `LAST` กับ "วันนี้ 00:00" ถ้าไม่มีไฟล์ ให้ใช้วันนี้ 00:00
  - รันซ้ำในวันเดียวกัน → รายงานยังครอบคลุมทั้งวัน (ไฟล์ของวันนี้ถูกเขียนทับด้วยฉบับล่าสุด)
  - รันครั้งแรกของวัน → รวมงานหลัง standup รอบก่อนด้วย (เช่น ช่วงค่ำเมื่อวาน หรือเสาร์–อาทิตย์)

## Step 2 — เก็บข้อมูลจาก session digest
ห้ามอ่านไฟล์ `.jsonl` ใน `~/.claude/projects` โดยตรง ให้ใช้ digest ที่ script เตรียมไว้
1. อัปเดต digest ให้ครบก่อน: `~/.claude/scheduled-tasks/daily-standup/session-digest.sh --sweep`
2. Digest อยู่ที่ `$STANDUP_OUT_DIR/sessions/YYYY-MM-DD/<project>__<session>.md` หนึ่งไฟล์ต่อหนึ่ง session ต่อหนึ่งวัน ให้อ่านทุกไฟล์ในโฟลเดอร์วันที่ตั้งแต่วันของ `SINCE` ถึงวันนี้ อ่านทั้งไฟล์ ไม่ต้องตัดต้นตัดท้าย
3. ในโฟลเดอร์วันของ `SINCE` ให้นับเฉพาะหัวข้อ `### HH:MM` ที่เวลาหลัง `SINCE`
4. หัวไฟล์บอก Project, path, Branch ถ้ามีบรรทัด `Continues earlier work. First prompt ...` แปลว่าเป็น session ที่ทำต่อจากวันก่อน ใช้บรรทัดนั้นเพื่อเข้าใจว่าเป็นงานอะไรเท่านั้น ห้ามนับเป็นงานของรอบนี้
5. จดว่าแต่ละ session: ทำอะไร / เสร็จหรือค้าง / เจอ error ที่ยังแก้ไม่ได้หรือรอคนอื่นไหม
   - session ที่ทดสอบ ตรวจการ์ด หรือหาสาเหตุของปัญหา เป็นงาน แม้ไม่มี commit เลย
   - session ที่ทดสอบหลายการ์ด ให้จดผลแยกทีละการ์ด: เลขการ์ด ผ่านหรือไม่ผ่าน และสิ่งที่ยังรอ
6. ข้าม session ที่ไม่ใช่งาน เช่น แค่เปิด tool, ถามความรู้ทั่วไป, ปรับ config/memory ส่วนตัวของ Claude
7. ถ้าไฟล์ `$STANDUP_OUT_DIR/sessions/.errors.log` มีบรรทัดที่เวลาหลัง `SINCE` ให้แจ้งใน Problems ว่า digest ของบาง session อาจไม่ครบ

## Step 3 — เก็บข้อมูลจาก git ในเครื่อง
1. หา repo: `find $STANDUP_REPO_ROOTS -maxdepth 4 -name .git -prune 2>/dev/null` และเพิ่ม repo จาก path ในหัวไฟล์ digest ของ Step 2 ที่อยู่นอกโฟลเดอร์เหล่านี้
2. แต่ละ repo:
   - Commit ของเราในช่วงเวลา:
     `git log --all --since="$SINCE" --author="$(git config user.email)" --date=format:"%d/%m %H:%M" --pretty=format:"%h|%ad|%D|%s" --shortstat`
   - งานที่ยังไม่ commit: `git status --short` และ `git diff --stat` → ใช้เป็นข้อมูล Plans
   - branch ปัจจุบัน และ push แล้วหรือยัง: `git branch --show-current`, `git rev-parse --abbrev-ref @{u}`
3. ข้าม repo ที่ไม่มีความเคลื่อนไหวในช่วงเวลา

## Step 4 — วิเคราะห์และจัดกลุ่ม
- **เริ่มจาก session digest แล้วใช้ git ยืนยันสถานะ** ห้ามสรุปจาก git อย่างเดียว เพราะงานทดสอบและงานตรวจไม่มี commit
- ก่อนเขียน ให้ไล่รายการ session ที่เป็นงานจาก Step 2 ทีละอัน ทุกอันต้องมีที่อยู่ในรายงาน
- **จัดกลุ่มเป็น "เรื่อง"** (topic) = 1 ticket หรือ 1 feature/งานใหญ่ เช่น `[EX-123] AI Agent — Knowledge base`, `LLMs-friendly Docs`
  - ดึงเลข ticket (regex `[A-Z][A-Z0-9]+-\d+`) จากชื่อ branch, commit message และชื่อ/เนื้อหา session ถ้ามีให้ใส่ในชื่อเรื่อง
  - งานที่ไม่มี ticket ให้ตั้งชื่อเรื่องตาม feature/branch เป็นภาษาที่ PO เข้าใจ
  - งานเล็กที่ไม่เข้าเรื่องไหน รวมไว้ในเรื่อง `🛠 อื่น ๆ`
  - ทดสอบหลายการ์ดในรอบเดียว (เช่น การ์ดทั้ง sprint) = 1 เรื่อง ตั้งชื่อว่า `🧪 ทดสอบ sprint <ชื่อ> ครบ N ใบ` และวางเป็นเรื่องแรกของ Progress
  - ดึงชื่อการ์ดจาก tracker ของทีม ถ้า tool ยังไม่โหลด ให้โหลดด้วย ToolSearch ก่อน (เช่น `select:mcp__<tracker>__get_task`) ห้ามตั้งชื่อการ์ดเอง
  - ใช้ชื่อเรื่องเดียวกันทุกหัวข้อ (Progress / Plans / Problems) เพื่อให้ AI ของ PO จับคู่ได้
- รวม commit + session ที่เป็นงานเดียวกันเป็น bullet เดียว ไม่ต้องลิสต์ทุก commit (ดูกฎ 1 เรื่อง = 1 ประโยค ใน Step 5)
- **Progress** = งานที่ได้ผลแล้วในช่วงเวลานี้ จะมี commit หรือไม่มีก็ได้ งานทดสอบ งานตรวจ และงานหาสาเหตุที่ได้คำตอบแล้ว นับเป็น Progress
- **Plans** = งานที่ค้าง (โค้ดยังไม่ commit, ยังไม่ push/MR, branch WIP, session จบกลางทาง) + สิ่งที่จะทำต่อพรุ่งนี้ รวมเป็น bullet เดียวต่อเรื่อง ใส่ % คร่าว ๆ เฉพาะเมื่อมีหลักฐานชัด
- **Problems** = blocker ที่มีหลักฐาน (error ที่ยังแก้ไม่ได้, รอ spec/API/review จากคนอื่น) + คำถามที่รอ PO ตัดสินใจ ห้ามแต่งขึ้นเอง ถ้าไม่มีให้เขียน `ไม่มี 🎉`
- งานที่ทำต่อจากวันก่อนให้รายงานเฉพาะส่วนที่ทำในช่วงเวลานี้ และต่อท้ายว่า `(ต่อจากเมื่อวาน)`
- งานที่ไม่ได้ทำวันนี้ (อยู่ในช่วงเวลาเพราะทำหลัง standup รอบก่อน) ให้ต่อท้าย bullet ว่าทำเมื่อไร เช่น `(เมื่อวานช่วงค่ำ)` หรือ `(เสาร์)`

## Step 5 — เขียนรายงาน
กฎการเขียน:
- ภาษาไทย ศัพท์เทคนิคใช้ภาษาอังกฤษได้
- เขียนเป็น "ผลลัพธ์ที่ได้" ไม่ใช่ชื่อไฟล์ เช่น "หน้า Login เชื่อม API ได้แล้ว" แทน "แก้ LoginPage.tsx"
- **1 เรื่อง = 1 bullet = 1 ประโยคสั้น ต่อหัวข้อ** ห้ามแตกเรื่องเดียวกันเป็นหลาย bullet
  - ยกเว้นเรื่อง `🧪 ทดสอบ ...` และ `🛠 อื่น ๆ` ที่มี 1 bullet ต่อ 1 การ์ด
  - bullet ของการ์ด = เลขการ์ด + ผลที่ได้ + สถานะหรือสิ่งที่ยังรอ เช่น `- EX-212 key 8 แบบผ่าน แต่เลือกโมเดลไม่ได้ เพราะ BE ยังไม่รับ provider ใหม่`
  - ห้ามย่อ `🛠 อื่น ๆ` เหลือแค่สถานะ ❌ `- EX-544 รวมเข้าแล้ว · EX-543 เปิด Draft` ✅ `- [EX-544 Resend link](url) สมัครด้วยอีเมลที่ยังไม่ยืนยันแล้วได้ลิงก์ใหม่ รวมเข้าแล้ว`
- ชื่อการ์ดในบรรทัดชื่อเรื่องและใน `🛠 อื่น ๆ` เป็นลิงก์ `[KEY ชื่อการ์ด](url)` ถ้ามีไฟล์กฎเรื่องลิงก์การ์ดใน `~/.claude/rules/` ใช้รูปแบบ URL จากไฟล์นั้น
- **ผลลัพธ์นำ แล้วตามด้วยสถานะหรือเหตุผล**: ขึ้นต้นด้วยสิ่งที่ได้ (มองจากมุมผู้ใช้/PO) ปิดท้ายด้วยสถานะ ("รอ deploy พุธ 4 พ.ย.") หรือเหตุผลถ้ายังใช้ไม่ได้ ("แต่ยังเปิดใช้ไม่ได้ เพราะ…")
- ยาวไม่เกิน ~100 ตัวอักษร (ประมาณ 15–25 คำ) ห้ามร้อยหลายขั้นตอนต่อกันด้วยคอมมา
- ตัดขั้นตอนระหว่างทางที่ PO ไม่ต้องใช้ตัดสินใจ (สร้าง draft ใน CMS, ตัด tag, ลง CR Sheet, ชื่อ task เช่น T9, test x/x) ใส่เลข MR/เวอร์ชันเฉพาะเมื่อ PO ต้องใช้อ้างอิง
- Blocker = ปัญหาที่กระทบผู้ใช้/งาน + สิ่งที่ต้องทำเพื่อปลด + `→ @คนที่ต้องทำ`
  - ❌ `- สร้าง draft 3 หัวข้อใน CMS, แก้ให้ลิงก์ #section เลื่อนถึงหัวข้อ (ผ่าน staging), ตัด tag v1.1.4, ลง CR Sheet และอัปเดตการ์ดว่าต้อง build+deploy ด้วย`
  - ✅ `- เอกสาร 3 หัวข้อใหม่พร้อมขึ้นจริงแล้ว รอ deploy วันพุธ 4 พ.ย.`
  - ✅ `- หน้าซื้อ Point และจ่ายบัตรทำเสร็จแล้ว แต่ยังเปิดใช้ไม่ได้ เพราะระบบส่งแพ็กเกจรายเดือนมาแทน Top-up`
  - ✅ Blocker: `- ลูกค้าเชื่อม Instagram บน prod ไม่ได้ ต้องแก้ค่า redirect บน server → @BE/DevOps`
- ใช้หัวข้อตาม template เป๊ะ ๆ ทุกวัน (PO ใช้ AI สรุปต่อ โครงสร้างต้องคงที่)
- ใต้แต่ละหัวข้อ ใส่ชื่อเรื่องเป็นบรรทัดตัวหนา `**emoji ชื่อเรื่อง**` แล้วตามด้วย bullet ของเรื่องนั้น ข้ามเรื่องที่ไม่มีอะไรในหัวข้อนั้น
- บรรทัด `> **สรุป:**` บนสุด = 1–2 เรื่องที่สำคัญที่สุดของวัน คั่นด้วย ` · `
- ห้ามใช้คำเหล่านี้ใน Progress/สรุป: AC, MR, tag, beta, test x/x, e2e, simplify, code review, ADR, ชื่อ branch
- header ใช้ชื่อโปรเจกต์ที่ PO เรียก (เช่น Dev Portal, Web App) ไม่ใช่ชื่อ repo
- Progress แสดงไม่เกิน 4 เรื่อง ที่เหลือรวมใน `🛠 อื่น ๆ`
- Plans เขียนแบบ "ทำถึงไหน → พรุ่งนี้ทำอะไร"
- ใน Problems สิ่งที่รอ PO ตอบให้ขึ้นต้นด้วย `🙋 PO:` และเป็นคำถามที่ตอบได้ทันที วางไว้ก่อน blocker อื่น
- มีแค่ 3 หัวข้อ ไม่มีหัวข้อ Notes ข้อมูลที่ PO ต้องรู้ให้ใส่ใน Problems ที่เหลือตัดทิ้ง
- เรียกคนด้วยชื่อเล่นแบบข้อความธรรมดา เช่น `@พี่<ชื่อเล่น>` เพราะรายงานนี้ส่งใน Discord ห้ามใช้ handle จริงหรือ `<@ID>` ที่จะ ping คนทุกครั้ง
- ห้ามใส่ secret, token, ค่าใน .env, ข้อมูลลูกค้า, IP/hostname ของ server, path ส่วนตัว หรือเรื่องสุขภาพ/ส่วนตัวของคนอื่น (ใช้คำว่า "ลางาน" แทน "ลาป่วย")

**ปรับคำด้วย unslop ก่อนนับความยาว**
- อ่าน `~/.claude/plugins/marketplaces/cursor-plugins/pstack/skills/unslop/SKILL.md` ด้วย Read แล้วแก้ทุกประโยคในรายงานตามกฎในไฟล์นั้น เป็นภาษาไทย (Skill tool เรียก skill นี้ไม่ได้ ต้องอ่านไฟล์เอง)
- ถ้าไม่เจอไฟล์ ให้หาด้วย `find ~/.claude/plugins -path '*pstack*/skills/unslop/SKILL.md'` ถ้ายังไม่เจอ ให้บอกในบรรทัดใต้ code block ว่ารอบนี้ไม่ได้ปรับคำ
- ส่วนที่ template กำหนดให้คงไว้: emoji ในหัวข้อและบรรทัดชื่อเรื่อง ตัวหนาของบรรทัดชื่อเรื่อง `→` ใน Plans และ Problems และ ` · ` ในบรรทัดสรุป
- ข้อความนอก code block และฉบับแก้ทุกฉบับใน session เดียวกัน ใช้กฎเดียวกัน

**รายงานเป็นข้อความเดียว ยาวไม่เกิน 2000 ตัวอักษร** (นับทั้งข้อความ รวม header) ห้ามแยกเป็นหลายส่วนแบบ (1/2) ถ้าเกิน ให้ตัดตามลำดับนี้จนพอดี:
1. ย่อประโยคของแต่ละเรื่องให้สั้นลง (ยังคง 1 ประโยคต่อเรื่อง)
2. ตัดรายละเอียดตัวเลข/ชื่อเทคนิคที่ PO ไม่จำเป็นต้องรู้
3. ถอดลิงก์ของ bullet ในเรื่อง `🧪 ทดสอบ ...` เหลือแค่เลขการ์ด ลิงก์ในบรรทัดชื่อเรื่องและใน `🛠 อื่น ๆ` ให้คงไว้
ห้ามตัด Problems ห้ามตัดเรื่องหรือการ์ดออกจาก Progress และห้ามย่อ `🛠 อื่น ๆ` เหลือแค่สถานะ

Template:

```

- สิ่งที่ทำเสร็จ (ผลลัพธ์ + สถานะ)
**🛠 อื่น ๆ**
- [KEY ชื่อการ์ด](url) ผลที่ได้ + สถานะ (1 bullet ต่อ 1 การ์ด)

### 🚧 Problems
- 🙋 PO: คำถามที่ตอบได้ทันที
- ปัญหา + สิ่งที่ต้องทำเพื่อปลด → @คนที่เกี่ยวข้อง (หรือ "ไม่มี 🎉") — ถ้ามีไฟล์ทีม `~/.claude/teams/*.md` ที่ `repos:` ตรงกับ repo นั้น ใช้ชื่อเล่นจากไฟล์
```

## Step 6 — บันทึกและแสดงใน chat
ไม่มี webhook ผู้ใช้ copy รายงานจาก chat ไปโพสต์ Discord เอง ห้ามโพสต์ไปที่ไหนเอง
1. นับความยาวจริงก่อน (เช่น `python3 -c "import sys;print(len(open(sys.argv[1]).read()))" <file>`) ถ้าเกิน 2000 ให้กลับไปตัดตาม Step 5
2. บันทึกไฟล์ที่ `$STANDUP_OUT_DIR/YYYY-MM-DD.md` (วันที่ของ `NOW`) เขียนทับได้ถ้ารันซ้ำวันเดียวกัน
3. บันทึกเวลารอบนี้: `printf '%s\n' "$NOW" > "$STANDUP_OUT_DIR/.last-run"` ถ้ารอบนี้ล้มเหลวกลางทาง ห้ามเขียนไฟล์นี้ เพื่อให้รอบถัดไปเก็บงานช่วงนี้ซ้ำ
4. **ข้อความสุดท้ายของ session ต้องมีรายงานฉบับเต็มอยู่ในตัวข้อความ** ใน code block เดียว (```` ``` ````) ให้ copy ไปวาง Discord ได้ทันที
   - ผล `cat` ใน Bash หรือไฟล์ที่ส่งแนบ ผู้ใช้มองไม่เห็นใน chat ไม่นับว่าแสดงแล้ว ต้องพิมพ์รายงานลงในข้อความตอบเอง
   - ถ้าใช้ tool ปิดรอบ (เช่น wrap_up) ให้เรียกก่อน แล้วค่อยเขียนข้อความสุดท้ายที่มีรายงาน
   - ถ้าไม่พบงานเลย ให้บอกสั้น ๆ ว่าไม่พบ commit หรือ session แทนรายงาน
5. ใต้ code block เขียนบรรทัดเดียว: บันทึกไฟล์ที่ไหนและยาวกี่ตัวอักษร ถ้ามีจุดที่ควรเช็กก่อนโพสต์ (เช่น ชื่อคนที่ไม่แน่ใจ) ใส่ได้ไม่เกิน 2 ข้อ ห้ามพูดเรื่อง webhook หรือ Discord และห้ามมีรายการหมายเหตุเพิ่ม

## ถ้าผู้ใช้ขอแก้รายงานใน session เดียวกัน
- แก้จากฉบับล่าสุดที่ผู้ใช้เห็น ถ้าผู้ใช้วางฉบับของตัวเองมา ให้ใช้ฉบับนั้นเป็นฐาน
- เก็บรายละเอียดทุกบรรทัดที่มีอยู่ ตัดเฉพาะส่วนที่ผู้ใช้สั่งตัด ถ้าต้องตัดเพื่อให้ลง 2000 ให้ตัดตามลำดับใน Step 5
- ฉบับแก้ยังเป็นข้อความเดียว ไม่เกิน 2000 ตัวอักษร ผ่าน unslop และบันทึกทับไฟล์ของวันนี้
