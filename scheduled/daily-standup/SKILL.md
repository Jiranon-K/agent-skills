# Daily Standup Report

สร้างรายงาน Daily Standup จากงานจริงที่ทำ แล้วจัดรูปแบบสำหรับโพสต์ใน Discord
ผู้อ่านคือ PO ที่อ่านเองบนมือถือและให้ AI สรุปต่อ PO ต้องตอบได้ในครึ่งนาทีว่า วันนี้ได้อะไร พรุ่งนี้ทำอะไร ติดอะไร โครงสร้างจึงคงที่ทุกวัน และทุกบรรทัดอ่านเข้าใจได้โดยไม่ต้องเปิดโค้ดหรือเปิดการ์ด

## Config (อ่านจาก environment ถ้ามี ไม่มีให้ใช้ค่า default)
- `STANDUP_NAME` — ชื่อที่แสดง (default: `git config --global user.name`)
- `STANDUP_REPO_ROOTS` — โฟลเดอร์ที่เก็บ repo คั่นด้วย space (default: `~/Projects`)
- `STANDUP_OUT_DIR` — ที่เก็บไฟล์รายงานและ session digest (default: `~/Documents/work/standups`)

## Step 1 — กำหนดช่วงเวลา
ใช้ timezone Asia/Bangkok
- `NOW` = เวลาที่เริ่มรัน (`TZ=Asia/Bangkok date "+%Y-%m-%d %H:%M"`) จดไว้ใช้ใน Step 6
- `LAST` = เนื้อหาของไฟล์ `$STANDUP_OUT_DIR/.last-run` (รูปแบบ `YYYY-MM-DD HH:MM`)
- `SINCE` = ค่าที่เก่ากว่าระหว่าง `LAST` กับ "วันนี้ 00:00" ถ้าไม่มีไฟล์ ให้ใช้วันนี้ 00:00
  - รันซ้ำในวันเดียวกัน → รายงานยังครอบคลุมทั้งวัน (ไฟล์ของวันนี้ถูกเขียนทับด้วยฉบับล่าสุด)
  - รันครั้งแรกของวัน → รวมงานหลัง standup รอบก่อนด้วย (เช่น ช่วงค่ำเมื่อวาน หรือเสาร์–อาทิตย์)

## Step 2 — เก็บข้อมูลจาก session digest
ห้ามอ่านไฟล์ `.jsonl` ใน `~/.claude/projects` โดยตรง ให้ใช้ digest ที่ script เตรียมไว้
1. อัปเดต digest ให้ครบก่อน: `~/.claude/scheduled-tasks/daily-standup/session-digest.sh --sweep`
2. Digest อยู่ที่ `$STANDUP_OUT_DIR/sessions/YYYY-MM-DD/<project>__<session>.md` หนึ่งไฟล์ต่อหนึ่ง session ต่อหนึ่งวัน ให้อ่านทุกไฟล์ในโฟลเดอร์วันที่ตั้งแต่วันของ `SINCE` ถึงวันนี้ อ่านทั้งไฟล์ ไม่ต้องตัดต้นตัดท้าย
3. ในโฟลเดอร์วันของ `SINCE` ให้นับเฉพาะหัวข้อ `### HH:MM` ที่เวลาหลัง `SINCE`
4. หัวไฟล์บอก Project, path, Branch ถ้ามีบรรทัด `Continues earlier work. First prompt ...` แปลว่าเป็น session ที่ทำต่อจากวันก่อน ใช้บรรทัดนั้นเพื่อเข้าใจว่าเป็นงานอะไรเท่านั้น ห้ามนับเป็นงานของรอบนี้
5. จดว่าแต่ละ session: ทำอะไร / เสร็จหรือค้าง / เจอ error ที่ยังแก้ไม่ได้หรือรอคนอื่นไหม
   - session ที่ทดสอบ ตรวจการ์ด หรือหาสาเหตุของปัญหา เป็นงาน แม้ไม่มี commit เลย
   - session ที่ทดสอบหลายการ์ด ให้จดผลแยกทีละการ์ด: เลขการ์ด ผ่านหรือไม่ผ่าน และสิ่งที่ยังรอ
6. ข้าม session ที่ไม่ใช่งาน เช่น แค่เปิด tool, ถามความรู้ทั่วไป, ปรับ config/memory ส่วนตัวของ Claude
7. ถ้าไฟล์ `$STANDUP_OUT_DIR/sessions/.errors.log` มีบรรทัดที่เวลาหลัง `SINCE` ให้แจ้งใน `ติดอะไร` ว่า digest ของบาง session อาจไม่ครบ

## Step 3 — เก็บข้อมูลจาก git ในเครื่อง
1. หา repo: `find $STANDUP_REPO_ROOTS -maxdepth 4 -name .git -prune 2>/dev/null` และเพิ่ม repo จาก path ในหัวไฟล์ digest ของ Step 2 ที่อยู่นอกโฟลเดอร์เหล่านี้
2. แต่ละ repo:
   - Commit ของเราในช่วงเวลา:
     `git log --all --since="$SINCE" --author="$(git config user.email)" --date=format:"%d/%m %H:%M" --pretty=format:"%h|%ad|%D|%s" --shortstat`
   - งานที่ยังไม่ commit: `git status --short` และ `git diff --stat` → ใช้เป็นข้อมูลของ `พรุ่งนี้ทำอะไร`
   - branch ปัจจุบัน และ push แล้วหรือยัง: `git branch --show-current`, `git rev-parse --abbrev-ref @{u}`
3. ข้าม repo ที่ไม่มีความเคลื่อนไหวในช่วงเวลา

## Step 4 — จัดเป็นรายการงาน
- **เริ่มจาก session digest แล้วใช้ git ยืนยันสถานะ** ห้ามสรุปจาก git อย่างเดียว เพราะงานทดสอบและงานตรวจไม่มี commit
- **1 งาน = 1 การ์ด หรือ 1 feature** รวม commit และ session ของงานเดียวกันเป็นงานเดียว ไม่ลิสต์ทีละ commit
  - ดึงเลขการ์ด (regex `[A-Z][A-Z0-9]+-\d+`) จากชื่อ branch, commit message และชื่อ/เนื้อหา session
  - อ่านการ์ดจาก tracker ของทีมให้รู้ว่างานคืออะไร ถ้า tool ยังไม่โหลด ให้โหลดด้วย ToolSearch ก่อน (เช่น `select:mcp__<tracker>__get_task`) ห้ามเดาจากเลขการ์ด
  - ตั้ง **ชื่องาน** เป็นคำไทยที่ PO ใช้เรียกงานนั้น ไม่เกิน 40 ตัวอักษร เช่น การ์ด `EX-193 Test chat records which topic or agent answered (backend)` ได้ชื่องาน `Test chat บอกว่า topic ไหนตอบ` ห้ามวางชื่อการ์ดภาษาอังกฤษทั้งบรรทัด
  - งานเดียวกันใช้ชื่องานเดียวกันทั้งสามหัวข้อ เพื่อให้ PO และ AI ของ PO จับคู่ได้
- ให้สถานะหนึ่งอย่างต่อหนึ่งงาน:
  - ✅ เสร็จ = ผลอยู่ในที่ที่ตั้งใจแล้ว (รวมเข้า branch หลักแล้ว ขึ้น staging หรือ production แล้ว หรืองานหาสาเหตุที่ได้คำตอบแล้ว)
  - 🔄 ทำต่อ = ทำไปแล้วแต่ยังไม่เสร็จ (โค้ดยังไม่ commit ยังไม่ push ยังไม่เปิด MR หรือ session จบกลางทาง)
  - 🧪 ทดสอบ = ทดสอบหรือตรวจการ์ด หนึ่งการ์ดเป็นหนึ่งงาน
- จัดงานเข้าโปรเจกต์ด้วยชื่อที่ PO เรียก (เช่น Dev Portal, Web App) ไม่ใช่ชื่อ repo
- `วันนี้ทำอะไร` = ทุกงานที่แตะในช่วงเวลานี้ ทั้งสามสถานะ
- `พรุ่งนี้ทำอะไร` = ก้าวถัดไปของงาน 🔄 และงานใหม่ที่จะเริ่ม ใส่เฉพาะที่มีหลักฐานใน session หรือการ์ด
- `ติดอะไร` = blocker ที่มีหลักฐาน (error ที่ยังแก้ไม่ได้, รอ spec/API/review จากคนอื่น) และคำถามที่รอ PO ตัดสินใจ ห้ามแต่งขึ้นเอง
- งานที่ทำต่อจากวันก่อน รายงานเฉพาะส่วนที่ทำในช่วงเวลานี้ และต่อท้ายว่า `(ต่อจากเมื่อวาน)`
- งานที่ไม่ได้ทำวันนี้ (อยู่ในช่วงเวลาเพราะทำหลัง standup รอบก่อน) ต่อท้ายว่าทำเมื่อไร เช่น `(เมื่อวานช่วงค่ำ)` หรือ `(เสาร์)`
- **ตรวจความครบก่อนเขียน** ไล่ session ที่เป็นงานจาก Step 2 และ repo ที่มี commit จาก Step 3 ทีละอัน ทุกอันต้องมีบรรทัดใน `วันนี้ทำอะไร` ห้ามตัดงานออกเพราะเป็นงานเล็กหรือเพราะรายงานยาว

## Step 5 — เขียนรายงาน

Template (ใช้หัวข้อและลำดับนี้ทุกวัน):

```

- 🔄 **ชื่องาน** [KEY](url) ทำถึงไหนแล้ว
- 🧪 **ชื่องาน** [KEY](url) ผ่านหรือไม่ผ่าน และสิ่งที่ยังรอ
```

ตัวอย่างบรรทัด:
- ✅ `- ✅ **Test chat บอกว่า topic ไหนตอบ** [EX-193](url) ขึ้น staging แล้ว รอ release`
- ✅ `- 🧪 **เชื่อม WhatsApp** [EX-112] ใส่ token ผิดแล้วขึ้นข้อความเตือนถูกต้อง รอบัญชีจริงทดสอบอีก 2 เคส`
- ✅ `- **ปล่อย release 6.45.0** ระบบหลังบ้านอีก 2 ส่วนยังไม่ขึ้น เลยกำหนด 12:00 แล้ว → @พี่<ชื่อเล่น>`
- ❌ `- EX-212 ทดสอบแล้ว` (ไม่บอกผล)
- ❌ `- สร้าง draft 3 หัวข้อใน CMS, แก้ลิงก์ #section, ตัด tag v1.1.4, ลง CR Sheet` (เล่าขั้นตอน ไม่บอกผล)
- ❌ `- EX-110 copy ยังเป็นอังกฤษ → @A · EX-112 รอ ID จริง → @B` (สองเรื่องในบรรทัดเดียว)

กฎของบรรทัด:
- **1 งาน = 1 บรรทัด = 1 ประโยค** ต่อหัวข้อ ไม่เกิน ~90 ตัวอักษรไม่นับลิงก์ ห้ามร้อยหลายขั้นตอนด้วยคอมมา
- ขึ้นต้นด้วยผลที่ผู้ใช้หรือ PO เห็น ปิดท้ายด้วยสถานะ ("รอ deploy พุธ 4 พ.ย.") หรือเหตุผลถ้ายังใช้ไม่ได้ ("แต่ยังเปิดใช้ไม่ได้ เพราะ…") เขียนผลลัพธ์ ไม่เขียนชื่อไฟล์ เช่น "หน้า Login เชื่อม API ได้แล้ว" แทน "แก้ LoginPage.tsx"
- บรรทัด 🧪 ต้องบอกว่าผ่านหรือไม่ผ่าน และผ่านเรื่องอะไร
- ภาษาไทย ศัพท์เทคนิคเป็นอังกฤษได้เมื่อ PO ใช้คำนั้นเอง
- ห้ามใช้คำเหล่านี้: AC, MR, tag, beta, rc, test x/x, e2e, simplify, code review, ADR, back-merge, promote, ชื่อ branch, ชื่อ repo, เลข MR ยกเว้นในบรรทัด `ติดอะไร` ที่คนรับต้องใช้เลขอ้างอิง ให้ใส่ในวงเล็บท้ายบรรทัด
- ตัดขั้นตอนระหว่างทางที่ PO ไม่ต้องใช้ตัดสินใจ (สร้าง draft ใน CMS, ตัด tag, ลง CR Sheet, ชื่อ task เช่น T9)
- ลิงก์การ์ดใช้เลขการ์ดเป็นข้อความลิงก์ `[KEY](url)` วางหลังชื่องาน ใส่เฉพาะใน `วันนี้ทำอะไร` ถ้ามีไฟล์กฎเรื่องลิงก์การ์ดใน `~/.claude/rules/` ใช้รูปแบบ URL จากไฟล์นั้น งานที่ไม่มีการ์ดไม่ต้องมีลิงก์
- เรียกคนด้วยชื่อเล่นแบบข้อความธรรมดา เช่น `@พี่<ชื่อเล่น>` ห้ามใช้ handle จริงหรือ `<@ID>` ที่จะ ping คนทุกครั้ง ถ้ามีไฟล์ทีม `~/.claude/teams/*.md` ที่ `repos:` ตรงกับ repo นั้น ใช้ชื่อเล่นจากไฟล์
- ห้ามใส่ secret, token, ค่าใน .env, ข้อมูลลูกค้า, IP/hostname ของ server, path ส่วนตัว หรือเรื่องสุขภาพ/ส่วนตัวของคนอื่น (ใช้คำว่า "ลางาน" แทน "ลาป่วย")

กฎของแต่ละส่วน:
- บรรทัด `-#` นับจากรายการงานจริง ตัวเลข ✅ 🔄 🧪 ต้องตรงกับจำนวนบรรทัดใน `วันนี้ทำอะไร` และ 🚧 ตรงกับจำนวนบรรทัดใน `ติดอะไร` ข้ามตัวที่เป็น 0
- `> **สรุป:**` ประโยคเดียว ถ้ามีเรื่องที่รอ PO ตอบ ให้เรื่องนั้นเป็นสรุป
- `วันนี้ทำอะไร` แบ่งด้วยบรรทัดตัวหนาชื่อโปรเจกต์ ถ้าทั้งวันมีโปรเจกต์เดียวไม่ต้องมีบรรทัดนี้ ในแต่ละโปรเจกต์เรียง ✅ ก่อน แล้ว 🔄 แล้ว 🧪
- `พรุ่งนี้ทำอะไร` ไม่เกิน 5 บรรทัด เรียงตามลำดับที่จะทำ
- `ติดอะไร` บรรทัด `🙋 PO:` มาก่อน หนึ่งปัญหาต่อหนึ่งบรรทัด ทุกบรรทัดบอกสิ่งที่ต้องการและจบด้วย `→ @คน` ถ้าไม่มีให้เขียน `ไม่มี 🎉`
- มีแค่ 3 หัวข้อ ไม่มีหัวข้อ Notes หรือ อื่น ๆ ข้อมูลที่ PO ต้องรู้ให้ใส่ใน `ติดอะไร`

**ปรับคำด้วย unslop ก่อนนับความยาว**
- อ่าน `~/.claude/plugins/marketplaces/cursor-plugins/pstack/skills/unslop/SKILL.md` ด้วย Read แล้วแก้ทุกประโยคในรายงานตามกฎในไฟล์นั้น เป็นภาษาไทย (Skill tool เรียก skill นี้ไม่ได้ ต้องอ่านไฟล์เอง)
- ถ้าไม่เจอไฟล์ ให้หาด้วย `find ~/.claude/plugins -path '*pstack*/skills/unslop/SKILL.md'` ถ้ายังไม่เจอ ให้บอกในบรรทัดใต้ code block ว่ารอบนี้ไม่ได้ปรับคำ
- ส่วนที่ template กำหนดให้คงไว้: emoji ของหัวข้อและของสถานะ ตัวหนาของชื่องานและชื่อโปรเจกต์ `→` ใน `ติดอะไร` และ ` · ` ในบรรทัด `-#`
- ข้อความนอก code block และฉบับแก้ทุกฉบับใน session เดียวกัน ใช้กฎเดียวกัน

**รายงานเป็นข้อความเดียว ยาวไม่เกิน 2000 ตัวอักษร** (นับทั้งข้อความ รวม header และ URL) ห้ามแยกเป็นหลายส่วนแบบ (1/2) ถ้าเกิน ให้ตัดตามลำดับนี้จนพอดี:
1. ย่อประโยคให้สั้นลง (ยังคง 1 ประโยคต่องาน)
2. ตัดตัวเลขและชื่อเทคนิคที่ PO ไม่ต้องใช้
3. ถอดลิงก์ของบรรทัด 🧪 เหลือเลขการ์ดเป็นข้อความ
4. ถอดลิงก์ของบรรทัดที่เหลือ เหลือเลขการ์ดเป็นข้อความ
ห้ามตัดบรรทัดงานออกจาก `วันนี้ทำอะไร` และห้ามตัดบรรทัดใน `ติดอะไร`

ถ้าไม่พบงานเลยในช่วงเวลา ให้รายงานสั้น ๆ ว่าไม่พบ commit หรือ session แล้วข้ามไป Step 6 ข้อ 3 อย่าแต่งเนื้อหา

## Step 6 — บันทึกและแสดงใน chat
ไม่มี webhook ผู้ใช้ copy รายงานจาก chat ไปโพสต์ Discord เอง ห้ามโพสต์ไปที่ไหนเอง
1. นับความยาวจริงก่อน (เช่น `python3 -c "import sys;print(len(open(sys.argv[1]).read()))" <file>`) ถ้าเกิน 2000 ให้กลับไปตัดตาม Step 5
2. บันทึกไฟล์ที่ `$STANDUP_OUT_DIR/YYYY-MM-DD.md` (วันที่ของ `NOW`) เขียนทับได้ถ้ารันซ้ำวันเดียวกัน
3. บันทึกเวลารอบนี้: `printf '%s\n' "$NOW" > "$STANDUP_OUT_DIR/.last-run"` ถ้ารอบนี้ล้มเหลวกลางทาง ห้ามเขียนไฟล์นี้ เพื่อให้รอบถัดไปเก็บงานช่วงนี้ซ้ำ
4. **ข้อความสุดท้ายของ session ต้องมีรายงานฉบับเต็มอยู่ในตัวข้อความ** ใน code block เดียว (```` ``` ````) ให้ copy ไปวาง Discord ได้ทันที
   - ผล `cat` ใน Bash หรือไฟล์ที่ส่งแนบ ผู้ใช้มองไม่เห็นใน chat ไม่นับว่าแสดงแล้ว ต้องพิมพ์รายงานลงในข้อความตอบเอง
   - ถ้าใช้ tool ปิดรอบ (เช่น wrap_up) ให้เรียกก่อน แล้วค่อยเขียนข้อความสุดท้ายที่มีรายงาน
   - ถ้าไม่พบงานเลย ให้บอกสั้น ๆ ว่าไม่พบ commit หรือ session แทนรายงาน
5. ใต้ code block เขียนบรรทัดเดียว: บันทึกไฟล์ที่ไหน ยาวกี่ตัวอักษร และรายงานครอบคลุมกี่ session กี่ repo ถ้ามีจุดที่ควรเช็กก่อนโพสต์ (เช่น ชื่อคนที่ไม่แน่ใจ) ใส่ได้ไม่เกิน 2 ข้อ ห้ามพูดเรื่อง webhook หรือ Discord และห้ามมีรายการหมายเหตุเพิ่ม

## ถ้าผู้ใช้ขอแก้รายงานใน session เดียวกัน
- แก้จากฉบับล่าสุดที่ผู้ใช้เห็น ถ้าผู้ใช้วางฉบับของตัวเองมา ให้ใช้ฉบับนั้นเป็นฐาน
- เก็บรายละเอียดทุกบรรทัดที่มีอยู่ ตัดเฉพาะส่วนที่ผู้ใช้สั่งตัด ถ้าต้องตัดเพื่อให้ลง 2000 ให้ตัดตามลำดับใน Step 5
- ฉบับแก้ยังเป็นข้อความเดียว ไม่เกิน 2000 ตัวอักษร ผ่าน unslop และบันทึกทับไฟล์ของวันนี้
